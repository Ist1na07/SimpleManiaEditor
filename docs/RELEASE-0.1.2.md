# 0.1.2：播放中跳转策略与性能

日期：2026-10-08（Asia/Taipei）。

## 结论

常规 1x 播放的主要瓶颈是策略：0.1.1 每次 seek 都使用停播级淡出、等待输出缓冲、销毁并重建设备；UI 的 12 ms 定时器和音频层的 24 ms debounce 还会叠加。连续滚轮会反复推迟提交。

0.25x 保音高另有真实 DSP 预热开销。两者必须分别处理，不能只调小一个定时器或用功能测试代替性能测量。

## 改动

- 普通 seek 复用输出设备、在音频读取边界切换解码/DSP 状态，不停止或排空设备。
- 3 ms 接缝渐变，由前一采样帧平滑过渡到新位置；真正 Play/Pause 的 5 ms 淡入淡出保留。
- 1x 即使勾选保音高也绕过不必要的时间伸缩。
- 慢倍率 phase-vocoder 使用独立解码器在读取锁外准备；准备期间旧音乐继续，准备完成后原子切换。已过时的准备请求可在提交前取消。
- 音频层合并窗口从 24 ms 减到 4 ms；界面按首个滚轮事件调度，不等整个滚轮串结束才提交。
- 侧栏全量刷新从滚轮同步路径移到合并的低优先级任务。

## 实测范围

同一 20 秒、16 kHz 单声道 WAV、模拟 5 ms 消费输出端，8 次定位：

| 1x、关闭保音高 | 0.1.1 | 优化后 |
| --- | --- | --- |
| 单次处理耗时中位数 | 63.50 ms | 0.14 ms |
| 最慢样本 | 79.67 ms | 4.57 ms |
| 8 次定位的设备重建 | 8 次 | 0 次 |

这是该测试夹具中的引擎操作耗时，**不是硬件端到端延迟，也不是对官方编辑器的同机对比**。每组仅 8 次，JSON 中的 `P95Ms` 实际为这组最慢样本，不用来估计总体尾延迟。原始记录保存在 [优化前](performance/seek-before.json)、[最终版本](performance/seek-release-final.json) 和 [格式测试](performance/seek-formats-final.json)。

生成音频转 WAV/MP3/Ogg 后还测试了 1x、0.5x、0.25x，全部 seek 复用设备。常规路径中位数在亚毫秒范围；0.25x 的后台准备依格式和 CPU 调度仍约 50～90 ms，8/8 次准备期间输出端都继续消费旧音频。该成本尚未消除，真实歌曲、较长文件与设备缓冲需要继续实测。

构建零警告、零错误，49/49 核心测试通过。界面回归覆盖播放保持、Space 暂停优先、原有精确删除/网格/反向 LN，以及接缝渐变的采样连续性；另覆盖 1x 与保音高变速之间切换、过时 DSP 准备取消后旧音频继续输出。

Windows x64 自包含便携版已验证发布目录及 ZIP 解压后的运行时、Skia、7K LN 读写；演示谱面、音频和性能记录齐全。

开发环境复测：运行 `scripts/Test.ps1`；UI 测试程序另支持 `--seek-benchmark <报告路径> [音频目录]`，提供 WAV/MP3/Ogg 目录可重复格式测试。
